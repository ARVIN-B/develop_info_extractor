## 3. Critical rules: No fabricated data

These rules are mandatory.

### Rule A — Never fabricate API responses

Never manually create a response and save it as if it came from a real source.

Never generate sample phone numbers, business names, addresses, websites, seller information, product data, IDs, or other values.

Never infer a response schema from:
- Package names
- Function names
- Documentation
- Tool descriptions
- Expected behavior
- Other sources
- Similar APIs

A documented field is not proof that the field actually appears in a real response.

### Rule B — Distinguish actual results from inferred information

Every output must have an explicit evidence status.

Use these statuses:

- `verified_live_response`: Captured directly from a successful real request.
- `verified_live_error`: Captured directly from an actual request that returned an error.
- `verified_tool_schema`: Retrieved directly from the running MCP server's tool definitions.
- `documented_only`: Found in documentation but not verified through a real request.
- `inferred`: Inferred from code or other indirect evidence.
- `not_tested`: No actual test has been performed.
- `requires_api_key`: Testing requires credentials that are not available.
- `requires_manual_configuration`: Additional setup is required.
- `unavailable`: The source could not be accessed or executed.

Never label `documented_only`, `inferred`, or `not_tested` data as verified.

### Rule C — Preserve original responses

When a source returns JSON:
- Save the original response.
- Do not remove null fields.
- Do not rename keys.
- Do not flatten nested objects.
- Do not remove empty arrays.
- Do not convert data types.
- Do not normalize phone numbers in the raw response.
- Do not remove metadata.
- Do not truncate long responses.

If the source returns text, HTML, XML, or another format, preserve the original content as faithfully as possible and record its actual content type.

You may create a separate normalized analysis file, but the original response must remain unchanged.

### Rule D — Report failures honestly

If a request fails:
- Save the actual error.
- Save the HTTP status code when available.
- Save the exception type and message.
- Save stderr and relevant process output for MCP failures.
- Record whether the failure occurred during startup, initialization, tool discovery, execution, authentication, parsing, or network access.
- Never replace an error with a fabricated successful response.

If no actual response is available, say so explicitly.

For each of the 10 sources, inspect every operation that can be discovered and safely executed.

Do not limit the investigation to one search function.

   - Input schema
   - Output schema, if available
   - Annotations, if available

9. Determine which tools perform:
   - Search
   - Business discovery
   - Business details
   - Phone/contact retrieval
   - Seller discovery
   - Product search
   - Company information
   - Pagination
   - Other relevant operations

Use the actual tool definitions to determine arguments. Never assume tool names or argument structures.

### B. Execute real requests

For each discovered tool:

- Determine whether it can be safely executed without credentials.
- If it requires arguments, construct valid test arguments based on its actual input schema.
- Use realistic test queries related to discovering businesses and their contact information.
- Use the same test query across comparable sources where practical.
- Save the exact arguments sent.
- Execute the actual tool.
- Save the complete raw response.

Do not invoke destructive operations, account modifications, purchases, messages, or other actions that could affect real users.

If a tool is not a search/read operation, inspect its schema but do not execute potentially destructive actions.

### C. API-based sources

For sources that do not expose MCP:

1. Inspect their actual implementation and integration code.
2. Identify their real API endpoints and request methods.
3. Identify authentication requirements.
4. Identify request parameters and headers.
5. Execute real read-only requests when configuration and credentials permit.
6. Capture actual status codes, headers where appropriate, and response bodies.
7. Record the exact request configuration, excluding secrets.

Do not invent endpoints or assume that a website's internal API is stable or publicly accessible.

If the integration cannot be executed, record the exact reason.

## 7. JSON output requirements

Every JSON file must be valid JSON.

Use UTF-8 encoding.

Preserve Persian text correctly.

Use `null` only when the original data actually contains null or when the metadata schema explicitly defines a missing value as null.

Do not confuse:
- Field absent
- Field present with null
- Field present with empty string
- Field present with empty array
- Field present with empty object

These are different states and must remain distinguishable.

For raw response files, preserve the original JSON structure.

For non-JSON responses, use an appropriate raw format and create a metadata JSON file that records the original content type and file location. Do not pretend that arbitrary text is JSON.
