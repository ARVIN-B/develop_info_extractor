# Task: Build a Complete Raw MCP Output Collector for All 10 MCP Sources

## 1. Main Objective

I want you to modify the existing project to build a runnable application that connects to all 10 configured MCP sources, discovers their available tools, executes all safely executable tools with valid arguments, and saves the actual responses returned by each MCP.

**The ONLY objective is to discover what data and JSON structures each MCP can return.**

I am NOT asking you to search for phone numbers, email addresses, websites, business names, addresses, or any other specific information.

I want to inspect the complete capabilities and actual outputs of these MCP servers first. We will analyze the returned data in a separate future phase.

Do not introduce any data-extraction or data-analysis logic.

## 2. Absolutely Forbidden Logic

Remove all existing logic related to searching for, detecting, extracting, identifying, classifying, or validating specific data fields.

In particular, completely remove:

- Phone-number detection.
- `phone`, `mobile`, `telephone` keyword matching.
- Email detection.
- Website detection.
- Address detection.
- Business/contact information detection.
- Any field-specific keyword matching.
- Any field inventory based on semantic categories.
- Any `contact_fields.json` generation.
- Any logic that decides whether a response contains useful contact information.
- Any logic that prioritizes a tool because it might return a particular field.
- Any filtering of response fields based on their names or values.

Do not replace these with another detection mechanism.

**The collector must not care what information exists inside a response. It must save everything.**

If an MCP returns 200 fields, preserve all 200 fields. If it returns nested objects, arrays, null values, unusual structures, or unexpected properties, preserve them exactly.

## 3. Discover Every MCP Tool

For each of the 10 MCP sources:

1. Connect to the MCP server.
2. Initialize the MCP session.
3. Retrieve the complete list of available tools.
4. Save every tool's original metadata:
   - Tool name.
   - Description.
   - Input schema.
   - Required parameters.
   - Optional parameters.
   - Parameter types.
   - Enumerations.
   - Default values, if provided.
   - Other metadata returned by the MCP server.

Do not simplify or rewrite the tool schemas.

I want to know exactly what each MCP makes available.

## 4. Execute All Safely Executable Tools

After discovering the tools, attempt to execute every tool that can safely be executed.

Important requirements:

- Do not execute only tools whose names contain `search`.
- Do not select tools based on assumptions about their purpose.
- Do not skip a tool merely because its name or description is unfamiliar.
- Do not assume that every MCP works like a search engine.
- Do not restrict execution to a predefined list of expected tools.
- Do not limit execution to tools that supposedly return business information.

Use the actual input schema returned by each tool to determine how it can be called.

### Argument handling

For every tool:

1. Inspect its actual input schema.
2. Identify required and optional arguments.
3. Use legitimate test values only when they are supported by the schema and the tool's documented purpose.
4. Do not invent identifiers, resource IDs, product IDs, business IDs, or other values that are supposed to come from a previous response.
5. If a tool requires an ID, first try to obtain that ID from a real response returned by another tool in the same MCP.
6. If no valid ID is available, record that the tool could not be executed because a required real identifier was unavailable.
7. If a tool requires authentication or unavailable external configuration, record the actual error and do not pretend the tool succeeded.
8. Never silently skip a tool.

Where a tool supports pagination, attempt to retrieve additional pages using the actual pagination parameters and values supported by its schema and responses.

Where a tool returns references to other resources, use those actual references to test relevant detail tools.

Where a tool supports multiple legitimate operations or argument combinations, test the supported combinations when practical.

Do not make up parameters that are not present in the schema.

### Safety

Do not execute destructive, write, delete, purchase, payment, posting, messaging, or other state-changing operations.

The objective is to inspect returned data, not to change anything in external services.

For tools whose behavior is unclear, inspect their description and schema. If their execution could change external state, do not execute them; record why.

## 5. Preserve Original MCP Responses

This is one of the most important requirements.

I want the actual responses returned by the MCP servers.

For every tool execution, save the complete original MCP response.

Preserve:

- The complete MCP result object.
- All content blocks.
- All text.
- All structured content.
- All embedded JSON.
- All nested objects and arrays.
- All metadata.
- All error information.
- All resource references.
- All pagination information.

Do not extract selected fields.

Do not convert the response into your own simplified schema.

Do not rename properties.

Do not discard properties that seem irrelevant.

Do not convert nested data into a flat structure.

Do not generate an artificial response based on the result.

Do not use an LLM to interpret or reconstruct responses.

If the MCP returns JSON encoded as a string inside a text block, preserve the original string exactly. You may optionally save a second decoded representation, but only if parsing succeeds without changing the original data. The original response must always remain available and unchanged.

**The original MCP response is the source of truth.**

## 6. Required Output: Exactly 10 Source Files

When the application finishes running, I want one JSON file for each of the 10 MCP sources.

Use the existing source names and configuration in the project.

The output structure should look similar to this:

```text
source_inspection/
    runs/
        <run_id>/
            neshan-mcp.json
            balad-mcp.json
            divar-mcp.json
            sheypoor-mcp.json
            basalam-mcp.json
            emalls.json
            rasmio.json
            iran-jobs.json
            torob.json
            digikala-mcp.json
```

There must be exactly one primary JSON file per MCP source.

Do not create separate primary output files for individual tools.

### Contents of each source file

Each file should contain:

- Source name.
- MCP connection and initialization status.
- Complete original tool definitions and schemas.
- List of all discovered tools.
- Execution status of each tool.
- Arguments actually sent to each tool.
- Complete original response returned by each tool.
- Errors returned by the MCP or encountered during execution.
- Reason for not executing a tool, if applicable.
- Pagination attempts and their original responses.
- Any relevant execution metadata, such as timestamps.

You may use a small wrapper to organize these records, but never modify the original tool definitions or MCP response payloads.

For example, the structure may look like this:

```json
{
  "source": "example-mcp",
  "connection": {
    "status": "initialized"
  },
  "tools": [
    {
      "name": "actual_tool_name",
      "original_definition": {},
      "executions": [
        {
          "arguments_sent": {},
          "status": "success",
          "original_mcp_response": {}
        }
      ]
    }
  ]
}
```

This is only an organizational example. Do not fabricate its contents. Populate everything using actual MCP responses.

If a source is unavailable, still create its JSON file and record the actual connection failure. Do not fabricate tool definitions or responses.

## 7. Execution Must Be Honest and Verifiable

I do not want fabricated results or optimistic success reports.

Follow these rules strictly:

- Never report a tool as successful unless it actually returned a successful response.
- Never report a source as initialized unless initialization actually succeeded.
- Never claim all tools were tested if some were skipped.
- Never fabricate sample responses.
- Never replace failed calls with manually generated JSON.
- Never hide errors.
- Never treat an empty response as a successful data retrieval unless that is what the actual MCP returned.
- Never assume that a tool is unavailable simply because one invocation failed.
- Never merge results from different execution runs.

Every execution must be traceable to an actual tool call.

## 8. Runtime Behavior

I want to run the collector with one command, for example:

```powershell
python scripts/inspect_sources.py --all
```

The application should:

1. Start all 10 configured MCP integrations.
2. Discover all available tools.
3. Save their original schemas.
4. Execute all safely executable tools.
5. Follow valid references and pagination where possible.
6. Save every actual response.
7. Create exactly 10 primary JSON files.
8. Print a concise execution summary.

One source failing must not prevent the other nine sources from running.

Use proper timeouts, exception handling, cleanup, and session termination.

Do not silently discard partial results if a source fails halfway through execution.
